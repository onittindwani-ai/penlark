# Limits and honest notes

- **The offline writer is templates.** It builds a skeleton and leaves brackets. It is not a language model, so a draft is only as good as what you add. The live model path (`LLM_BACKEND=anthropic`) is real code tested against a local mock server and recorded fixtures, and was never run with a real key: UNVERIFIED. A model draft is re scored by code and flagged, never auto approved, and the approval request refuses a draft under the minimum voice match.
- **The voice match is a style measure, not a taste judge.** It says how close the measured habits are to the profile. It cannot tell if the writing is good or true.
- **Held out numbers are from short sample texts** (<!--n:eval.voice.correct-->24<!--/n--> of <!--n:eval.voice.of-->24<!--/n--> correct author, mean AUC <!--n:eval.voice.auc-->0.975<!--/n-->). The same person wrote the samples and the test texts. A formal profile gave generic machine sounding prose a mean best score of <!--n:eval.voice.generic_mean_best-->79.0<!--/n-->, so a high match is not proof of a human voice. On two independent sets generic text still averaged about 61 (4 to 5 of 10 above the minimum of 60) and a punchy outsider passed the voice match 10 of 10; the house rules stopped all generic text. See `INDEPENDENT-EVAL.md`.
- **The banned phrase list catches what it lists.** A paraphrase such as "Turbocharge the potential of your cash flow" alone is not caught. Add your own phrases.
- **The claims check is strict but literal.** Every figure in a claim must appear as the same whole figure in an attached note: `5 percent` is not sourced by a note that says `15 percent` or `1500`, `1,500` and `1500` are the same, and `15%` and `15 percent` are the same. It does not know units (`10 hours` and `10 days` are both the figure 10) and does not match a figure written as a word to the same figure in digits. An experience claim needs a person to link a note. It cannot check that a note is true.
- **The idea finder is rules, and bounded.** It reads the newest 1,000 notes and at most 1 million characters (a note over 20,000 characters is cut), and keeps the 30 rarest words of each note, so one long call transcript cannot use the memory of the server (the worst case measured here was about 0.7 seconds and 160 MB). Older notes are left out of a run. On a real install the work runs in the worker, so the worker must be running; the offline demo answers inside the request. On held out notes it found <!--n:eval.ideas.themes_found-->2<!--/n--> of <!--n:eval.ideas.themes_total-->3<!--/n--> planted themes and leaked <!--n:eval.ideas.noise_leaked-->0<!--/n--> noise notes. Every evidence quote is verbatim (<!--n:eval.ideas.quotes_valid-->7<!--/n--> of <!--n:eval.ideas.quotes-->7<!--/n-->).
- **The learning loop describes, it does not explain.** With 60 posts it can miss real effects and the strict bar is on purpose. A pattern is a lead for an experiment.
- **Attribution counts clicks.** People who see a post and type the address later are not counted.
- **Scheduler adapters are untested against the real services.** Metricool's request shape is from memory.
- **LinkedIn and X export layouts are from memory** and unverified against a fresh export.
- **SQLite is the tested path for the full suites.** The migration was run up, down and up on Postgres 17 only.
- **Single tenant.** One workspace is one client.
- **Hosting.** The GitHub workflow builds the Docker images and starts the compose stack on a GitHub machine. No Vercel, Railway or Hetzner account was used, so the hosting guides are UNVERIFIED and the Caddy and backup files were never run on a real server.
- **A send that is cut off.** A draft is marked "being sent" before the scheduling tool is called, and a calendar row says so. If the app stops at that moment nothing says whether the post was made, so after 30 minutes the draft is held as "send unclear" (the audit log says why), exactly as if the tool had timed out: a person looks in the tool and presses **It was posted** or **It was not posted**. It is never put back to approved on its own, because a second click could then post it twice. The same hold applies when the tool answers with a success status but no post id (an error body, an empty list, a GraphQL `errors` list): the app cannot tell whether anything was queued, so it does not guess.
- **The voice profile build runs in the request.** It measures the newest 500 samples and at most 1.5 million characters of one voice (older ones are left out). A build at that limit took about 1.6 seconds of processor time here, so it is not queued for the worker; a very slow server will feel it. The page that adds a LinkedIn or X export checks each item against a set, not against every stored text.
- **The live match.** `/api/match` takes at most 30,000 characters and cost about 0.2 seconds at that length here.
- **DNS rebinding.** The scheduling tool's host is looked up and checked just before each call, but the call looks it up again to connect. A name that answers differently the second time is not defended against.
- **A slow call never holds the SQLite write lock.** A send to a scheduling tool, a model call (voice guide, draft variants, extra ideas) and the idea finder all let go of the write lock first and take it again, briefly, for the result, so another request can write while they wait. The cost of a model call is recorded in its own short transaction. A request still has one writer at a time, and a send is still one tool call after the claim is saved: use Postgres when several people write at once.
- **SQLite has no upgrade path for columns.** A file from an older version is detected at start (see `12-UPDATING.md`), but nothing converts a missing column. Version 1.0.1 adds no column. It adds one unique index (`uq_vp_conversion_lead_kind`, so one lead or customer event counts once): a SQLite file gets it at start, with repeated events already stored removed (the oldest of each is kept), and Postgres gets it from `alembic upgrade head` (revision 0002).
- **Pinned, not hashed.** `constraints.txt` fixes versions, not file hashes.
- **Uploads on Vercel.** The app accepts 8 MB; Vercel's documented 4.5 MB request limit applies first (not tested here, see `06-DEPLOY-VERCEL.md`).
- **PDFs.** A PDF is read inside the API process, with a cap of 8 MB, 200 pages and 2 million characters of text, and a 20 second budget checked between pages. A single page that is slow to read cannot be stopped from outside, so a hostile PDF can still make that one request slow (it does not hold the write lock or block other requests).
- **Rate limits are per process.** They are not shared between several API processes.
- **Two lead events at the same instant** with the same `lead_ref` and kind count once: the database has a unique index and the second event is answered as a duplicate.
- Not done: screen reader testing, a run on a real host, an independent security test.

- **Deleting is for the owner, and mostly through the API.** `DELETE /api/notes/{id}`, `/api/samples/{id}`, `/api/drafts/{id}`, `/api/authors/{id}` and `/api/performance` (one row, or all with `confirm=true`) remove the thing and the copies of its words the app made: a note leaves the ideas found from it (an idea found only from it goes, an idea that is kept gets a new title from the evidence that is left), the titles of the drafts made from it are cleared and so are the variants that quote it (the answer says how many), a sample takes every voice profile version built after it was added (they quote its sentences) and a new version is built from the rest with the plain guide (a locked version is lost, so lock the new one again), a draft takes its variants, calendar rows and exported file, a voice takes its samples, versions and drafts. Only the Library page has a button (for samples). What stays: a draft that quotes a deleted note keeps its own words (the answer lists the drafts that still quote it), the audit log keeps ids and counts and never held any text, and a draft that was sent, or may have been, cannot be deleted because its record is what stops a second send.
- **Deleting a sample can cost a hand edited guide, and numbers can repeat.** A deleted sample takes every profile version built after it, so a locked version whose guide you edited by hand is lost and a plain one is built in its place: lock and edit again. Version numbers are counted again from the versions that are left, so a number can be used twice over time. Not changed.
- **Large post number files are slow to import.** A CSV of about 150,000 rows is inserted one row at a time while the write lock is held (the file limit of 5 MB keeps a normal file far below that). Split a very large export. Not changed.
- **Click counts can be inflated.** A visitor is a day scoped hash of the address and the browser, so one person who changes their browser name between clicks counts as several unique visitors. The click route has a rate limit per address, but it is a count of clicks, not proof of people. Not changed.
- **Link guard limits.** A bare address with a file ending (`README.md`, `main.py`, `notes.rs`) is treated as a file name, not a web address, unless a path follows it. A capitalised sentence word after a full stop with no space (`Done.It works`) is not an address. Everything else that looks like `word.ending` with a known web ending in any capital letters or script, or any `word.word/path`, is flagged. Text like `https://[YOUR LINK]` is flagged and never stops the app.
- **Sending: the hour, the date and Buffer.** A send for a chosen day goes out at `SEND_HOUR` in `TIMEZONE` (default 9 in the morning UTC); a date and hour in the past are refused. Buffer is sent to its own queue or saved as a draft: Penlark has no verified way to give Buffer a time (the scheduled example was never readable, see `facts/buffer.md`), so a date with Buffer is refused instead of dropped.
- **A sent post stays on the calendar.** Only a planned item can be taken off the calendar. A sent or exported row is a record, and taking it away would put the draft back to approved so that a second click posted it twice. To take a post down, remove it in the scheduling tool yourself.
- **The idea finder and the hashing of the library are CPU work.** The finder runs in the worker with no write lock (on hostile notes it took about 6 seconds of processor time). Adding samples compares each against the digests of the library, read in batches on a worker thread, so a very large library makes an upload slower but never stalls the server.
- **The page security policy allows inline scripts.** The web app sends a Content-Security-Policy that allows only this app's own address for everything, but its scripts need `unsafe-inline` (the framework writes its start up data into the page, and the page sets the colour theme before it paints). Removing that needs a per request nonce, which would make every page render on the server for every visit. It was not tested in a real browser here: the browser checks run in CI.
- **Behind a platform proxy, set `FORWARDED_ALLOW_IPS`.** Without it every visitor reaches the API from the proxy's address and shares one rate limit bucket, so a few people can lock everyone out of the sign in page and tracked links. The app watches for this (requests that carry an `X-Forwarded-For` header from an address that is not in it) and shows a warning in the settings; a tracked link that hits the limit now says so (429) instead of "this link does not exist".
