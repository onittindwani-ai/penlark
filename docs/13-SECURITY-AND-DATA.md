# Security and data

- **Sign in** is required on every route except the sign in, the tracked link redirect and the signed lead webhook. Passwords are argon2 hashes. Sessions are signed, expire, and live in an httpOnly cookie set by the web app, which forwards to a private API.
- **Demo shortcuts.** The public demo password, the made up approver and viewer accounts, the demo buttons and the data reset exist only while `DEMO_MODE=true` and `OWNER_PASSWORD_HASH` is empty. Setting the hash switches all of them off at once, even if `DEMO_MODE` is left on. The reset also never erases the audit log, and is refused on a server database. A start with an example or short `SESSION_SECRET` (outside the demo) is refused before anything is written.
- **Sign in limits.** The email is compared without spaces or capitals, with a limit per address and account, per address alone and per account from anywhere; an unknown email costs the same work as a wrong password.
- **Two people.** The person who asks for an approval cannot decide it. The shared base refuses it (the same person cannot ask and decide) and a test in Penlark checks it through the route.
- **An approval is for the exact words.** The approver sees every character of the draft, and the approval keeps a fingerprint (SHA 256) of that text. If one character changes afterwards, deciding, exporting, planning on the calendar and sending are all refused until a second person approves the new text. On Postgres the draft row is locked while it is edited or decided, so the two cannot cross (SQLite has no row locks and runs one writer at a time).
- **Nothing publishes by itself.** Draft mode sends nothing. A send needs live mode, an approved draft whose text still matches its approval, and an explicit confirm. The kill switch (and the draft mode switch) set in the app are read from the database on every send, and the kill switch also stops the file export. A draft is claimed before the scheduling tool is called, so a second request cannot send it twice. The app can only pull the mode back, never push it forward.
- **Untrusted text.** Notes, comments and emails are data. They are checked as text and never trigger an action. In the live model path they are passed through the shared untrusted wrapper.
- **No open redirect.** A tracked link can only point at a host on your allow list, over https. The target is stored when the link is made and checked again on every click. The click request cannot change it.
- **Visitor privacy.** A click stores a hash of address, browser and date, never an address. The same person on another day counts as a new visitor.
- **Lead webhook.** HMAC SHA 256 signature, a size cap checked while the body arrives (a declared length first), and duplicate events ignored (the same `lead_ref` and kind counts once, so a replayed signed event adds nothing).
- **Text that could freeze the app.** A banned pattern must have an upper limit on every repeat and no repeat inside a repeat; one that does not is refused when added and shown, not run, if it is already stored. Pasted and uploaded text is read with bounded patterns. Uploads are read while they arrive and refused over 8 MB. PDF reading still runs in the API process (see `14`).
- **The visitor address.** The API trusts `X-Forwarded-For` only from the addresses in `FORWARDED_ALLOW_IPS`, and the web app passes on only the last entry. The public click route and the limits use that address, never the raw header.
- **Audit log.** Every change is chained to the one before. The Audit page can check the chain. On SQLite every request that can write takes the write lock when it starts, so two people saving at the same moment cannot fork the chain and show a tamper warning that is not real (reads never wait for it). On Postgres an advisory lock does the same.
- **A save is finished before the answer.** The database commit happens before the response is sent, so a save that fails (a locked file, a value that is too long) is an error the person sees, never a success message for a change that was lost.
- **A send with no clear answer is held.** A timeout, a server error or an unreadable reply from the scheduling tool leaves the draft in "send unclear": it cannot be sent again, edited or exported until a person looks in the tool and says whether the post was made. Only a refusal with a meaning (a 4xx answer) or a connection that never opened puts it back to approved.
- **The scheduling tool's address.** Only public https addresses are accepted, and the host is looked up each time the tool is called and refused if it points at a private address. `ALLOW_PRIVATE_SCHEDULER=true` is the deliberate way to use a Postiz on your own network. A name that changes its answer between the check and the connection (DNS rebinding) is not defended against.
- **Secrets.** Never printed, never in the text of the settings (`repr`), never in a start up error, never stored in the database. `tools/scan_secrets.py` scans the repo.
- **What stays on the vendor side.** Posts and tokens held by Postiz, Buffer or Metricool are governed by their own terms.

Your writing samples are stored in the database in plain text, because the engine measures them. Protect the database like the writing itself. Back up and delete it when the client leaves.

To remove one thing for good, the owner can delete a note, a writing sample, a draft, a voice or imported post numbers (see `14`). A deletion takes the copies of its words that the app itself made: the ideas quoted from a note, the profile versions built after a sample, the variants, calendar rows and exported file of a draft. It does not reach copies you made outside the app (a file you copied from the export folder, a backup) or a draft that was written from a note and still quotes it. A draft that was sent cannot be deleted. Text with a NUL character has it taken out before it is stored, and a note, a sample or a draft is never shown in the audit log, which keeps ids and counts only.

The web app sends a Content-Security-Policy that allows only its own address for scripts, styles, images, fonts and requests, and no framing. Its scripts still need `unsafe-inline` (see `14`). Settings never print the database address, so a Postgres password does not appear in a log line or an error page.
